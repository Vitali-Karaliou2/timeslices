# Временны́е срезы

*Обучающее приложение по истории и практике разработки ПО, построенное для эпохи генеративного ИИ. Стартовый документ проекта. Редакция: 12.10.2026. (Markdown-копия TimeSlices_Project_Brief_RU.docx для чтения из CLAUDE.md.)*

## 0. Назначение этого документа

Этот документ — единственный обязательный контекст для нового проекта, в котором будет разрабатываться обучающее приложение, описанное ниже. Он написан так, чтобы его было достаточно: все нужные выводы из серии материалов по курсу Anthropic «AI Fluency for Builders» (далее — «серия») здесь повторены в сжатом виде, а ссылки на документы серии даны только для желающих углубиться.

Документ состоит из четырёх частей: **замысел** (разделы 1–4), **устройство** (разделы 5–9), **план работ** (разделы 10–13) и **оценка** (разделы 14–16).

Терминология: **трек** (направление обучения, например front-end), **срез** (временно́й срез — состояние технологии в узком интервале времени), **пример** (работающее приложение внутри среза), **реализация** (вариант одного примера, соответствующий конкретному срезу), **процесс** (визуализированная последовательность кадров, показывающая, как пример создавался или исполнялся), **кадр** и **стоп-кадр**.

## 1. Откуда взялся замысел

**Первое — об обучении.** Задачи, на которых раньше рос начинающий разработчик, — это ровно те задачи, которые теперь делегируются модели в первую очередь. Главный открытый вопрос: **как научиться судить о коде, не написав его много**.

**Второе — об истории.** Каждый пункт исторического обзора — это **переход**: было решение А, стало решение Б, и у перехода была причина. Отсюда желание **«потрогать переход руками»**: увидеть одну и ту же задачу, решённую до появления нового решения и после, в ограничениях своего времени.

**Третье — о стадиях.** Стадии 0→1 и 1→n; самое опасное место — переход между ними. Замысел сознательно построен в два этапа: быстрый 0→1 одним человеком с моделью, затем 1→n командой.

**Идея одной фразой.** Обучающее приложение, в котором история разработки ПО представлена как частично упорядоченная коллекция временны́х срезов, на каждом из которых — один или несколько работающих примеров, показывающих решение одной задачи «до» и «после» появления нового подхода, с визуализацией не только результата, но и процесса; при этом целью является не знание истории, а тренировка способности судить о чужом коде.

**Чем отличается от курса по истории IT.** Приложение проверяет, **может ли человек, увидев два решения одной задачи, объяснить, чем второе лучше первого, при каких условиях и какой ценой**. Критерий для каждого среза: **что из этого среза понадобится, чтобы проверить код, который напишет модель?** Если ответ «ничего», срез — музейный экспонат.

## 2. Для кого

Студенты и начинающие (точка входа — начало треков); разработчики со стажем на переподготовке (точка входа — поздние срезы и упражнения на проверку); сам автор как первый пользователь. Следствие: **одна программа с несколькими точками входа**.

## 3. Границы

**Входит:** история как последовательность переходов с примерами «до/после»; треки; визуализация процесса; контроль знаний в два этапа; роли обучаемый / экзаменатор / администратор (позже куратор); трек нейросетей как отдельное направление.

**Не входит:** обучение стеку как самоцель; сертификационные курсы; темы без контраста «до/после» (алгоритмы, математика); мягкие навыки; подробное воспроизведение исторических систем ради достоверности. Безопасность — как **сквозное свойство** поздних срезов, а не трек.

## 4. Что повторено из серии

Модель 4D (делегирование, описание, различение, добросовестность); шесть способностей билдера; цепочка описания; пять линз различения (работает ли; выдержит ли эксплуатацию; та ли это задача; хорош ли опыт; ответственно ли); код без понимания; узкое место — проверка; человек в контуре как конфигурация; стадии 0→1 и 1→n; ответ без понимания.

## 5. Структура верхнего уровня: коллекция срезов с частичным порядком

**5.1. Иерархия.** Коллекция → Трек → Срез → Пример.

**5.2. Частичный порядок.** Коллекция — **ориентированный ациклический граф** срезов, где ребро А→Б означает «Б предполагает освоенным А». У трека может быть несколько начал и концов; трек — **подграф**. Один срез может принадлежать нескольким трекам: вводится **тематический срез** (срез × трек) с собственным состоянием прохождения. Переход к срезу открывается, когда пройдены все его непосредственные предшественники. **Треки не изолированы**: межтрековые рёбра прокладываются вручную; модель предлагает, человек утверждает.

**5.3. Состояния тематического среза** (линейная шкала): Недоступен → Доступен → В процессе → Пройден → В процессе сдачи → Сдан с результатом → Ожидает подтверждения → Подтверждён экзаменатором. Для 0→1 достаточно первых четырёх.

**Повторное прохождение.** Вернуться к пройденному срезу можно в режиме повторения. Если дальше не продвигался — срез возвращается в «в процессе». Если продвигался — выбор: (1) полный сброс последующих в «недоступен» либо (2) ничего не менять: срез «в процессе» с пометкой «повторно», для последующих по-прежнему пройден.

## 7. Устройство среза и примера

**7.1. Страница среза:** что это за срез (годы, треки, одна фраза о решении); связь с предыдущими; ссылка вперёд; **пометка актуальности** — (а) используется и в коде современных моделей; (б) вытеснено, но без него непонятны последующие; (в) исторично, для контекста; список примеров по возрастанию сложности; раскрывающийся список реализаций.

**7.2. Пример и реализации.** Пример — задача и одна или несколько реализаций, каждая привязана к срезу. **Пример вводится на одном срезе и может быть «отыгран назад» на более ранние и вперёд на более поздние**; функциональность прежняя, меняется решение.

**7.3. Процесс: кадры и стоп-кадры.** Два типа: **процесс исполнения** и **процесс создания** (с альтернативами: RUP против итераций). Эталонный пример для отработки формата — **прогон программы в 1970-х** с перфокартами: кадры с датой и временем, объяснением длительности; многочасовое ожидание проигрывается за секунды. На стоп-кадре — фрагмент кода с пояснением.

**7.4. Два режима кода:** исполняемый непосредственно (HTML/CSS/JS, Python, C#) и эмулируемый (машинный код, ассемблер, FORTRAN, COBOL, LISP — через эмуляцию или готовые результаты). Дублирование на Python — не раньше четвёртого этапа.

## 8. Контроль знаний: два этапа с человеком в контуре

**8.1.** Проверять надо не артефакт, а понимание: автоматическая сортировка, затем человек.

**8.2. Этап 1: автоматический.** Задания по примерам; **никаких вопросов с выбором ответа**; ответы в свободной форме, оценивает модель, обоснование показывается. **Основной защитный механизм — вопросы по собственному ответу пользователя.** Время и вставка фиксируются как признаки, не наказывают. Нет лимита времени и нет запрета идти дальше.

**8.3. Этап 2: экзаменатор.** Отдельная роль; уведомление со ссылкой на ответы, оценку, обоснование, признаки, историю и рекомендацию одного из пяти типов. Рекомендацию пользователь не видит. Калибровка — доля согласия экзаменаторов. **На 0→1** — демонстрационный режим: экзаменатор = администратор со списком сдач и двумя кнопками.

**8.4.** Схема переносится на школьные предметы и экзамены.

## 9. Технические решения и схема данных

**9.1. Оболочка и примеры — разные вещи.** Оболочка — одно приложение (ASP.NET с аутентификацией и ролями, тонкая). Примеры — **изолированные статические сборки**, встраиваемые через iframe; оболочка не знает, на чём написан пример. Каждый пример — папка с манифестом; оболочка читает манифесты.

**9.2. Эмуляция: не строить, а брать готовое.** Учебная машина с десятком команд; трансляторы в WebAssembly; для перфокарт — визуализация с готовыми результатами. **Достоверность процесса важнее достоверности машины.**

**9.3. Схема данных (черновик):** Track; Slice (годы, название, решение, актуальность, тексты; предшественники DAG; треки); ThematicSlice (Slice × Track); Example; Implementation (срез, стек, путь к сборке, код, пояснения); Process (тип, вариант); Frame (порядок, дата/время, текст, стоп-кадр, содержимое); User (роль, закреплённый экзаменатор); UserSliceState; Attempt; Question/Answer; ContributedExample.

## 10. С чего начинать: стадия 0→1

**10.1. Цель:** доказать полезность, реализуемость, масштабируемость.

**10.2. Первый набор из шести срезов:** Статическая страница ~1995 (front-end; пасьянс desktop vs страница); Формы и первая динамика ~1999 (вторая реализация); AJAX 2005 (межтрековое ребро, стоп-кадр на обмене запросами); Цикл процессора и регистры (учебная машина; процесс исполнения); Прогон 1972 года с перфокартами (эталонный процесс; эмулируемый код); Одно решение двумя процессами: RUP против итераций ~2001 (процесс создания).

**10.3. Определение готовности среза:** страница со всеми полями 7.1; хотя бы один пример с работающей реализацией; хотя бы один процесс с ≥1 стоп-кадром; проверка на анахронизмы **человеком**; ≥5 вопросов с эталонными обоснованиями; ответ «что из этого нужно, чтобы проверять код модели».

**10.4. Не делать на 0→1:** экзаменатор дальше демо; эмуляция настоящих машин; дублирование на Python; пользовательские примеры; распределённость и масштаб; **но** вести контекстный файл, записи решений и приёмочные критерии с первого дня.

## 13. Трек нейросетей и генеративного ИИ

Отдельный проект: персептрон → Минский → backprop → зимы → глубокое обучение → трансформер → законы масштабирования → LLM → агенты → XAI. Строится вокруг **чередования ожиданий и разочарований**. Замыслы автора: дообучение малых моделей для узбекского и белорусского; верификация шагов решения математических задач на языке, близком к логическому программированию (вместо Lean).

## 14. Оценка: риски

1. Историческая достоверность против ясности — защита только человеком; пометки «ПРОВЕРИТЬ ДАТУ»; темп ограничен пропускной способностью проверяющего.
2. Взрыв объёма — определение готовности, первый набор из шести, по одному с полной проверкой.
3. Подмена цели (музей) — обязательный ответ «зачем для проверки кода модели».
4. Стоимость эмуляции — готовые средства, учебная машина.
5. Защита от несамостоятельности — вопросы по собственному ответу; признаки фиксируются, но не наказывают.
6. Переход 0→1 → 1→n — контекстный файл, ADR, приёмочные критерии с первого дня.
7. Устаревающее содержание — пометка даты и правило пересмотра.

**Не учтено:** уровень «упражнение на проверку» (вот код модели для этого среза — найдите несоответствия); связь с реальными инструментами (получить тот же пример от Claude Code и сравнить); содержательное «пройти» на 0→1 (абзац «чем после лучше до и какой ценой»); авторские права на загруженные материалы; название (рабочее — TimeSlices).

## 15. Организация-партнёр

EPAM: быстрое подтверждение на 0→1; команда на 1→n как опыт командной разработки с ГенИИ; архивы компании как источник примеров; применение внутри компании до монетизации. Предложение строить как **содержание и методику**, встраиваемые в существующую инфраструктуру.

## 16. Первые шаги в новом проекте

1. Создать проект; загрузить этот документ.

6. Добавить остальные пять срезов по одному, с проверкой достоверности после каждого.
7. Записать, что в формате среза и процесса пришлось изменить.
