# 0013. Заголовки разделов страницы среза и «Справка»
Дата: 2026-10-19. Статус: proposed (решения автора по существу — 19.10.2026, п. 26; формулировки ниже ждут утверждения).

## Контекст
Автор, просматривая net-01 как первый пользователь (`Редактирование_обучающего_контента/net-before-web-example-1-1.docx`),
сделал два замечания, которые не решаются правкой текстов.

1. **Заголовки разделов страницы среза** зашиты в `Slice.cshtml`: «Вводимое решение», «Актуальность»,
   «Связь с предыдущими», «Дальше». Для стартового среза трека «вводимое решение» звучит неуместно,
   потому что ничего не вводится, а описывается сложившееся положение. «Актуальность» понятнее как вопрос:
   «Как это связано с сегодняшним днём?». Порядок разделов не следовал формуле «до → решение → после».
   Порядок уже исправлен правкой шаблона в PR #16; здесь он закрепляется.
2. **Справочные сведения, общие для нескольких срезов.** К одной строке `% ftp -d ftp.phys.example.edu`
   у автора возникли вопросы о DNS, доменах верхнего уровня, национальных доменах, `.edu` тогда и сейчас.
   Ответы — это не текст кадра: они длиннее пояснения стоп-кадра и понадобятся из других срезов
   (fe-01 с адресом `http://phys.example.edu/staff/`, позже AJAX, облако). В схеме нет места,
   где такой текст живёт один раз, а срезы на него ссылаются.

Варианты обсуждены 19.10.2026. Автор выбрал вариант 3 для заголовков и вариант 1 для справки.

## Решение

### А. Заголовки разделов
1. **Порядок разделов страницы среза:** «до» (`linkBack` и предшественники) → решение (`introduces`) →
   «после» (`linkForward` и последователи) → актуальность (`relevance`, `relevanceNote`, «зачем это,
   если код пишет модель») → примеры. Порядок задаёт шаблон и в схеме не настраивается.
2. **Новые заголовки по умолчанию** — интерфейс оболочки (`Pages/Labels.cs`), пометки ЧЕРНОВИК не несут
   (как подписи проигрывателя, ADR 0008). Предложение:

   | Раздел | Было | По умолчанию (предложение) |
   |---|---|---|
   | `linkBack` | Связь с предыдущими | Что было до |
   | `introduces` | Вводимое решение | Что меняется |
   | `linkForward` | Дальше | Что будет после |
   | `relevance` | Актуальность | Как это связано с сегодняшним днём? |
   | примеры | Примеры | Примеры |

3. **Замена в конкретном срезе** — необязательное поле `headings` в `slice.json`: объект, ключи только
   `linkBack`, `introduces`, `linkForward`, `relevance`, значения — непустые строки до 80 символов.
   Пропущенный ключ — заголовок по умолчанию. Заменяется только подпись: раздел, его место и содержание
   остаются прежними. Заголовки из `slice.json` — текст среза, поэтому их можно помечать `ЧЕРНОВИК:`,
   и они показываются со значком по ADR 0009.

   Для net-01 (подписи утверждены автором 19.10.2026):
   ```json
   "headings": {
     "linkBack":    "С чего начинаем",
     "introduces":  "Что представлял собой Интернет к началу 1990-х",
     "linkForward": "Что изменится с появлением HTTP",
     "relevance":   "Что осталось актуальным и в 2020-е"
   }
   ```
4. Валидатор: `headings`, если есть, — объект; неизвестный ключ, пустое значение и строка длиннее
   80 символов — ошибки.

### Б. «Справка»
5. **Новая единица содержания — справочная статья.** Название в интерфейсе — «Справка»; не «Справочник»,
   потому что так называется пример `directory`. Статьи — содержание, а не код оболочки:
   `Content/reference/<article-id>/article.json`. Папка, а не файл, чтобы позже положить рядом картинку
   или схему.
6. **Схема `article.json`:**
   ```json
   {
     "id": "dns",
     "title": "Система имён DNS",
     "summary": "ЧЕРНОВИК: как имя машины превращается в числовой адрес и кто за какую часть имени отвечает",
     "sections": [
       { "id": "1992", "heading": "Как было к 1992 году", "asOf": 1992,
         "paragraphs": ["ЧЕРНОВИК: ...", "ЧЕРНОВИК: ..."] },
       { "id": "now", "heading": "Как сейчас", "asOf": null,
         "paragraphs": ["ЧЕРНОВИК: ..."] }
     ],
     "see": ["top-level-domains", "internet-before-web"],
     "sources": [ { "title": "RFC 1034", "url": "https://www.rfc-editor.org/rfc/rfc1034" } ],
     "status": "draft"
   }
   ```
   - `sections[].asOf` — год, к которому относится раздел; `null` значит «сейчас». Справка тоже привязана
     ко времени: срез 1992 года ссылается на раздел «как было к 1992», и обучаемый не путает эпохи.
   - Текст — массив абзацев, без Markdown: разметка потребовала бы библиотеки или своего разборщика,
     а на 0→1 новых зависимостей не заводим. Ссылки внутри абзацев не поддерживаются; связи статей
     задаёт список `see`.
   - `sources` показываются обучаемому под статьёй («Источники»). Они нужны и автору для проверки дат.
   - `status`: `draft` → `reviewed` (era-reviewer) → `approved` (автор), как у срезов.
7. **Ссылки на статьи:**
   - из среза — необязательное поле `refs` в `slice.json`: массив, элемент — `"dns"` или `"dns#1992"`
     (статья или её раздел). На странице среза — строка «Справка: …» после раздела «Что меняется».
   - из стоп-кадра — необязательное поле `detail.refs` в `process/*.json` в том же формате. В панели
     стоп-кадра и в списке кадров без JS — строка «Справка: …» под пояснением. Ссылка открывается
     в новой вкладке, чтобы не сбивать проигрывание.
8. **Страницы:** `/reference` — список статей; `/reference/{id}` — статья, разделы с якорями `#<section-id>`,
   «См. также» и «Где упоминается» (срезы и кадры, которые ссылаются на статью; список строит
   `ContentCatalog`). Справка доступна любому вошедшему пользователю независимо от состояния срезов.
   В «Где упоминается» недоступный срез показывается названием без ссылки.
9. **Целостность:** ссылка на несуществующую статью или раздел — ошибка загрузки каталога, как ссылка
   на несуществующий срез. Есть тест на настоящем содержании. Валидатор проверяет `article.json`.
10. **Первый набор статей** (решение автора): `internet-before-web`, `dns`, `top-level-domains`, `ftp`.
    Ссылки: из net-01 (`refs` среза — `internet-before-web`; стоп-кадр 2 — `top-level-domains#1992`,
    `ftp#1992`; стоп-кадр 3 — `dns#1992`) и из fe-01 (стоп-кадр с адресом — `dns#1992`). Тексты статей —
    черновики; все даты в них проверяет автор (ПРОВЕРИТЬ ДАТУ), как в срезах.

## Последствия (включая то, что стало труднее)
- **Схема меняется** в трёх местах: `slice.json` (`headings`, `refs`), `process/*.json` (`detail.refs`),
  новый файл `article.json`. Все новые поля необязательные, старое содержание остаётся верным.
  `docs/spec/manifest-schema.md` обновляется в сессии, которая это реализует.
- Схема данных (БД) не меняется: справка не участвует в состояниях прохождения и контроле знаний.
- Появляется третий вид содержания, который проверяют era-reviewer и автор. Статьи растут быстрее
  срезов, поэтому нагрузка на проверку дат растёт. Защита: статья появляется только тогда, когда на неё
  ссылается хотя бы один срез.
- Заголовки по-разному на разных срезах — риск разнобоя. Он ограничен: разделы и их порядок
  фиксированы, заменяется только подпись, и замена — исключение (сейчас только net-01).
- Без Markdown в абзацах нельзя выделить слово или вставить ссылку посреди текста. Если это станет
  мешать, отдельный ADR введёт минимальную разметку.

## Альтернативы, которые отвергнуты, и почему
- **Заголовки:** только сменить подписи для всех срезов — стартовый срез всё равно говорит о «перемене»;
  признак `kind: "start"` с двумя жёсткими наборами — конкретные заголовки автора («Что изменится
  с появлением HTTP») в наборы не помещаются.
- **Справка как особый трек из «срезов-статей»** — у срезов есть вопросы, предшественники и состояния
  прохождения; справке они не нужны и мешали бы.
- **Только раскрывающиеся пояснения в кадрах** — схема не меняется, но текст о DNS пришлось бы повторять
  в каждом срезе, где встречается адрес.
- **Статья одним файлом `<id>.json`** — проще, но картинку или схему к статье пришлось бы класть отдельно
  от неё.
