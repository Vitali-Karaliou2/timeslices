# 0011. Контроль знаний на 0→1: самопроверка по эталону и демо-экзаменатор
Дата: 2026-10-19. Статус: accepted (решения автора 19.10.2026; вступает в силу при слиянии PR).

## Контекст
Brief 8.2–8.3 описывает контроль знаний в два этапа: автоматический (ответ в свободной форме
оценивает модель, затем вопросы по собственному ответу) и экзаменатор. Вопросы с эталонными
обоснованиями уже лежат в `questions.json` трёх срезов, но интерфейса нет. Автор хочет пройти весь
путь сам — как обучаемый и как экзаменатор — чтобы проверить полезность замысла (brief 10.1).
Оценка ответов моделью требует API-ключа и отложена.

## Решение
1. **Самопроверка вместо оценки моделью.** Обучаемый отвечает в свободной форме; ответ сохраняется;
   только после этого показываются эталонное обоснование и вопрос-продолжение по его ответу
   (`followUpTemplate` с подстановкой `{answer}`). Ответ на продолжение тоже сохраняется. Затем
   обучаемый сам отмечает, насколько его ответ совпал с эталоном: «совпал», «частично», «не совпал».
   Вариантов ответа нет (brief 8.2).
2. **Признаки самостоятельности фиксируются, но не наказывают** (brief 8.2; решение автора):
   время с показа вопроса до отправки, активное время ввода, число вставок из буфера обмена —
   для основного ответа и для ответа на продолжение. **Обучаемому они не показываются**;
   экзаменатору видны. На доступ и состояния не влияют.
3. **Эталонное обоснование никогда не уходит в браузер до сохранения ответа** — это проверяется
   на сервере и тестом.
4. **Состояния сдачи** (brief 5.3, сокращённо) выводятся из попытки, а не хранятся в
   `UserSliceState`: «в процессе сдачи» (попытка начата) → «ожидает подтверждения» (отправлена) →
   «подтверждён экзаменатором» или «возвращён» (с комментарием). «Сдан с результатом» пропускается:
   автоматической оценки нет. Сдача не открывает и не закрывает следующие срезы.
5. **Демо-экзаменатор** (brief 8.3): роли Examiner и Admin видят все отправленные попытки; по каждой —
   ответы, продолжения, самооценки, признаки, эталоны; две кнопки — «Подтвердить» и «Вернуть»
   (комментарий обязателен при возврате). Закреплённый экзаменатор, пять типов рекомендаций,
   калибровка — после 0→1.
6. **Регистрация в Development** без подтверждения почты; новый пользователь — Learner;
   администратор назначает роль на странице `/admin`. В Production подтверждение остаётся.

## Схема данных (EF Core, новая миграция)
- `Attempt`: `Id`, `UserId`, `SliceId`, `TrackId`, `StartedAt`, `SubmittedAt?`, `Status`
  (`InProgress` | `Submitted` | `Confirmed` | `Returned`), `ExaminerId?`, `ExaminerComment?`, `DecidedAt?`.
- `Answer`: `Id`, `AttemptId`, `QuestionId` (id из `questions.json`), `Text`, `FollowUpText?`,
  `SelfRating?` (`Match` | `Partial` | `NoMatch`), `ShownAt`, `AnsweredAt`, `ActiveMs`, `PasteCount`,
  `FollowUpActiveMs?`, `FollowUpPasteCount?`.
- Вопросы и эталоны в БД не копируются — они читаются из `questions.json` по `QuestionId`.

## Последствия
- Путь «пройти срез → ответить → сдать → подтвердить» можно пройти одному человеку в двух ролях.
- Оценка моделью добавится потом как ещё одно поле `Answer` (оценка и обоснование модели) без
  переделки этой схемы.
- Если `questions.json` изменится после сдачи, ответы ссылаются на `QuestionId`; при отсутствии
  вопроса экзаменатор видит пометку «вопрос удалён».
